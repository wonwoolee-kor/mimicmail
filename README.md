# Mimicmail

과거에 사용자가 보낸 이메일에서 수신자·관계·직책·목적이 유사한 문체 예시를 찾아 현재 대화에 맞는 초안을 작성합니다. Rust와 SQLite를 사용합니다. 웹 화면과 SQLite 라이브러리는 실행 파일에 포함되며, 실행 시 Python이나 별도 서버 런타임이 필요하지 않습니다. 모델을 별도로 학습하지 않고, 검색된 발신 메일을 생성 시 참조합니다.

## 프로젝트 구조

```text
src/           Rust 파싱·분류·검색·생성·HTTP 서버·CLI
assets/        웹 화면, 모델 지시문, SQLite 스키마
tests/         Rust 기능·HTTP·CLI·기존 데이터 호환성 테스트
history/       과거 발신 .eml 보관용 선택 폴더
data/          메일 본문·인용 대화·문체 참조 DB
Cargo.toml     빌드 설정
Cargo.lock     의존성 버전 고정
Mimicmail.command  macOS 실행 파일
```

과거 문체 자료는 SQLite에 보관합니다. 현재 수신 메일은 지정한 원본 경로나 세션의 표준 입력에서 읽어 메모리에서 처리하고, 초안은 표준 출력으로 반환합니다. 프로젝트에 현재 메일이나 초안을 별도 저장할 필요가 없습니다.

## 채팅형 메일 편집기

Finder에서 `Mimicmail.command`를 더블 클릭하거나 Codex에 “메일 GUI 열어줘”라고 요청합니다. 내부 실행 명령은 다음과 같습니다.

```sh
./target/release/mimicmail gui
```

기본 주소는 `http://127.0.0.1:8765`입니다. 이 기기에서만 접속하며 서버를 종료하려면 실행 중인 터미널에서 Ctrl+C를 누릅니다. 실행 중인 앱은 해당 주소로 다시 열 수 있습니다.

- 왼쪽에서 **수신자별 대화**를 선택하면 오른쪽에 날짜순 메일 말풍선과 상대방 이름이 표시됩니다. 이름·직급·제목·본문 및 인용문으로 대화를 검색할 수 있습니다. 제목·본문이 일치하면 목록에 해당 부분을 표시하며, 대화를 누르면 일치하는 제목·본문을 모두 강조합니다. 상단의 일치 개수와 이전·다음 버튼, 검색란의 Enter·Shift+Enter로 이동하며 해당 본문이 접혀 있으면 펼칩니다. 필터나 검색에서 제외된 대화는 선택이 해제됩니다.
- 목록의 **답장·인용** 표시는 `In-Reply-To`, `References`, 본문에 포함된 인용 대화를 기준으로 합니다. 상대방 글은 왼쪽, 내 글은 오른쪽에 표시합니다. 메시지 본문은 최대 180px까지 미리 보이며, 넘치는 본문은 아래 **더 보기 / 접기** 버튼으로 전환합니다. 짧은 메시지에는 토글이 표시되지 않습니다. 발신자·시각·본문이 같은 인용 메시지는 하나로 합치며, 같은 문장이라도 다른 시각에 보낸 메일은 유지합니다.
- 인용문은 독립된 수신 메일 원본이 아니라 보낸 메일 안에 남은 대화입니다. 헤더에서 작성자를 확인할 수 없는 인용문은 **작성자 미확인**으로 표시합니다. 보관함에 없는 답장을 생성하거나 대화가 완전하다고 가정하지 않습니다.
- 대화 상단의 **직급 지정**을 눌러 교수·팀장·연구원 같은 라벨을 직접 입력합니다. 같은 직급의 대화를 왼쪽 필터로 모아 볼 수 있으며, **미지정**은 라벨이 없는 대화만 표시합니다. 대화는 기본 무채색이며 라벨 편집 창의 슬라이더로 빨강부터 보라까지 색조를 지정할 수 있습니다. 색상은 OKLab의 원통 좌표인 OKLCH에서 명도 0.60을 유지하고 채도 목표를 0.12로 높여 색조만 25°~305° 범위에서 바꿉니다. 화면 색역을 벗어나는 색은 명도와 색조를 유지한 채 채도만 표현 가능한 범위로 제한합니다. 왼쪽 목록은 원형 프로필에만 색을 적용하고, 목록 배경과 선택 표시는 무채색을 유지합니다. 색상은 같은 라벨 전체에 적용되고 재실행 후에도 유지됩니다. 기존 색은 색조를 기준으로 같은 팔레트로 표시하며, 무채색은 색상 없음으로 표시합니다. **색상 없음**으로 무채색으로 되돌립니다. 목록의 라벨은 이름 오른쪽에 표시되며, 긴 이름과 라벨은 말줄임 처리됩니다. 전체 값은 마우스를 올리거나 대화를 열어 확인합니다. 라벨은 해당 상대방에게 보낸 메일 전체와 새로 색인할 메일에 적용되며, CLI 초안 작성에도 사용됩니다. `--role`을 지정하면 그 값이 우선합니다.
- 말풍선의 연필 버튼으로 **문체 참조 본문·관계·목적**을 편집하고 명시적으로 저장합니다. 저장된 변경은 이후 문체 검색에 반영됩니다. 원문과 인용 대화는 바뀌지 않습니다.
- 문서 버튼이나 편집기의 **전체 대화 원문** 탭에서 전체 본문을 읽습니다. 상대방 글은 문체 참조에 포함하지 않습니다. 파일을 다시 색인해도 저장한 편집본을 덮어쓰지 않습니다.
- 왼쪽 대화 목록 맨 위의 **+ 새 대화**에서 이름과 선택 사항인 직급을 입력하면 바로 시작합니다. 이메일 입력은 필요하지 않습니다. 발신 이력이 없어도 대화가 DB에 유지되며, 같은 보관함에서 같은 이름을 다시 입력하면 기존 대화를 엽니다. 직접 만든 대화는 상단 이름 옆 연필 버튼으로 이름을 수정할 수 있으며, 기존 답장과 직급은 유지됩니다. 새 대화 자체는 발신 메일이나 문체 자료로 저장하지 않습니다.
- 왼쪽 상단의 **설정**에서 **General context**를 키·값으로 추가·수정·삭제하고 저장합니다. 이름·소속처럼 같은 DB의 모든 대화에 공통으로 사용할 정보를 보관하며, 재실행 후에도 유지됩니다. `context` 조회와 CLI 초안 작성에 `current_facts.general_context`로 포함되고, 현재 작성 요청이 우선합니다. 키는 중복 없이 입력하며 이메일 주소는 기존 개인정보 처리 규칙에 따라 치환합니다.
- 아래 입력란에 작성할 내용을 쓰고 **프롬프트 복사**를 누릅니다. 복사 내용에는 **대화 이름·식별자(보관함·상대방 ID), 작성 요청, 이 README의 조회 방법을 참고하라는 지시**만 담습니다. 기본 DB 경로와 실행 명령은 생략하며, 별도 DB를 사용할 때만 경로를 표시합니다. 프로젝트 내부 경로는 상대 경로로 표시합니다. 메일 본문과 문체 예시를 클립보드에 포함하지 않습니다. Codex가 해당 프로젝트의 로컬 DB에서 필요한 자료를 직접 조회해 초안을 작성합니다.
- `context` 명령은 기본적으로 제목·날짜·목적 등의 후보 목록만 반환하며 과거 본문은 넣지 않습니다. 동일 인물의 이전 사실은 이번 요청에 필요한 경우에만 `--history-key KEY`로 선택합니다. 독립적인 요청에는 이전 대화를 참조하지 않습니다. 문체 예시는 `--style-id ID`로 필요한 항목만 조회합니다. 새 인물은 같은 라벨에 속한 모든 인물의 발신 이력을 후보로 삼으며, 후보를 먼저 5개로 잘라내지 않습니다. 라벨이 없거나 해당 라벨의 자료가 없으면 정중하고 간결한 기본 문체를 사용합니다. 삭제된 메시지는 후보와 본문 조회에서 모두 제외됩니다. 새 수신자의 사실관계로 다른 사람과의 대화를 가져오지 않습니다. 작성 요청과 프롬프트는 DB에 저장하지 않습니다.
- 작성 요청은 열린 페이지의 메모리에 발신 계정·수신자별로 보관해 대화를 이동해도 유지합니다. 작성 요청이 남아 있으면 페이지를 닫거나 새로고침할 때 확인하며, 실제로 페이지를 떠나면 요청은 사라집니다.
- 메일 작성 후 아래 입력란에서 **보낸 메일**을 선택해 본문을 붙여 넣고 **메일 저장**을 누르면 오른쪽 말풍선에 추가합니다. 저장한 본문은 대화 조회·검색·문체 참조에 포함되며 기존 메일처럼 문체 편집과 삭제가 가능합니다. 직접 입력한 내 메일과 상대 답장은 발신일시를 임의로 넣지 않고 저장 순서대로 표시합니다. 저장 전 내용은 작성 요청·상대 답장과 별도로 대화마다 페이지 메모리에 유지하며, 저장 실패 시에도 남습니다. 저장 후 입력란으로 돌아와 계속 입력할 수 있습니다. 이 기능은 메일 기록만 저장하며 이메일을 발송하지 않습니다.
- 아래 입력란에서 **상대 답장**을 선택해 받은 내용을 입력하고 **답장 저장**을 누르면 DB에 저장하며 왼쪽 말풍선으로 즉시 표시합니다. 직접 입력한 상대 답장은 수신일시를 저장하거나 표시하지 않고 저장 순서로 보여줍니다. 기존 DB의 해당 날짜 필드와 화면 조회용 캐시도 실행 시 제거합니다. 말풍선의 연필 버튼으로 본문을 수정하며, 다른 창에서 먼저 수정되었거나 삭제된 답장은 덮어쓰지 않습니다. 새 대화에서도 사용할 수 있고, 저장한 답장은 검색·선택한 대화 문맥 조회에 포함되며 삭제할 수 있습니다. 상대 답장은 내 문체 참조에 포함하지 않습니다. 저장 전 입력은 작성 요청과 별도로 대화마다 페이지 메모리에 유지하며, 저장 실패 시에도 남습니다. 페이지를 떠나면 저장 전 입력은 사라집니다.
- 왼쪽 대화 목록에서 우클릭하거나 **⋯**를 눌러 **대화 삭제**를 선택합니다. 대화 이름을 확인하고 삭제하면 목록·검색·문체 참조에서 제외되며, 보관 원문과 다른 상대방의 대화는 유지합니다. 새로고침·재실행·재색인 후에도 삭제 상태를 유지합니다. 같은 이름으로 새 대화를 만들면 이전 내용이 없는 별도 대화로 시작합니다.
- 각 메시지의 휴지통 버튼을 누르면 제목·발신자·발신 시각·본문 일부와 **정말 삭제하시겠습니까?** 확인 창이 뜹니다. **취소** 또는 Esc로 닫으면 변경되지 않으며, **메시지 삭제**를 눌러야 적용됩니다. 삭제한 메시지는 대화·검색·프롬프트·문체 참조에서 제외되고 같은 메시지의 반복 인용도 함께 제외됩니다. 보관된 원문과 원본 `.eml`은 유지하는 논리 삭제이며, 새로고침·재색인 후에도 삭제 상태를 유지합니다.
- 수정 중 닫으면 변경 사항을 버릴지 확인하며, 두 창에서 같은 메일을 수정하면 오래된 편집본의 저장을 막습니다.

### 날짜를 지정해 저장

```sh
./target/release/mimicmail --user me@example.com ingest /path/to/sent-mail --since 2026-01-01
```

`.eml`의 `Date` 헤더를 한국 시간으로 환산해 **2026-01-01 00:00부터 포함**합니다. 날짜가 없거나 해석할 수 없거나 시간대가 없는 메일은 날짜 조건을 확인할 수 없어 제외합니다. 파일 이름이나 수정 시각은 기준으로 사용하지 않습니다. 선택된 메일 안의 과거 인용 대화는 문맥 보존을 위해 함께 보관하되 별도 발신 메일로 색인하지 않습니다.

기본 DB는 `data/mimicmail.sqlite3`이며 폴더가 없으면 생성합니다. `--db`로 다른 경로를 지정할 수 있습니다. 메일 원본 파일과 첨부 파일은 복제하지 않고, 읽을 수 있는 본문·대화 연결 정보·문체 자료를 DB에 저장합니다. 이메일 주소는 저장하지 않습니다. 기존 DB는 실행 시 주소를 내부 인물 ID로 바꾸고 본문·인용 헤더·파일명 등에 남은 주소도 `[이메일 삭제됨]`으로 치환합니다. 이름·직급·메일 연결·삭제 상태는 유지하며, 새 색인과 편집에도 같은 처리를 적용합니다. 인물 ID는 주소의 단방향 해시이며 주소 매핑표는 저장하지 않습니다. 새 대화에는 임의 ID를 부여합니다. `context` 조회에는 복사된 프롬프트의 보관함·상대방 ID를 사용하며, 기존 CLI의 이메일 인수도 메모리에서 ID로 변환해 조회합니다. 원본 `.eml` 파일은 기존 위치에 그대로 유지됩니다.

## 실행

기본 엔진은 **Codex CLI**입니다. 프로젝트 폴더에서 실행하며, `codex`가 설치되어 있고 로그인되어 있어야 합니다. ChatGPT 계정으로 Codex에 로그인한 경우 별도의 OpenAI API 키 설정은 필요하지 않습니다. Codex 앱에서 아래 작업을 자연어로 요청해도 됩니다.

빌드에는 Rust 도구 모음이 필요합니다. 프로젝트 폴더에서 실행 파일을 한 번 빌드합니다. 빌드한 바이너리는 Rust 설치 없이 실행할 수 있습니다. `Mimicmail.command`도 바이너리가 없으면 최초 빌드를 수행합니다. 소스를 수정한 뒤에는 아래 명령으로 다시 빌드합니다.

```sh
cargo build --release --locked
```

### Codex 채팅에서 진행

1. 과거 발신 `.eml`이 있는 폴더를 지정합니다. 프로젝트의 `history/`를 사용해도 되고 기존 보관 위치를 그대로 사용해도 됩니다. 현재 수신 메일은 초안을 요청하는 세션에서 파일 경로 또는 원본 `.eml` 데이터로 전달합니다.
2. 아래 요청에서 이메일 주소를 실제 주소로 바꿔 Codex 채팅에 입력합니다.

   ```text
   내 기본 이메일은 me@example.com이야.
   history 폴더의 .eml 파일을 Codex 엔진으로 색인해줘.
   본인 발신 메일만 저장하고, 저장·건너뛴 건수를 알려줘.
   ```

3. 색인이 끝나면 초안 생성을 요청합니다.

   ```text
   이번 세션에서 전달한 수신 메일에 대한 답장을 만들어줘.
   내 이메일은 me@example.com, 수신자는 manager@example.com이야.
   상대방은 내 상사이고 직책은 팀장이야.
   검토에 감사하고 수정본을 2026년 11월 13일까지 전달하겠다는 내용으로 써줘.
   Codex 엔진과 기존 문체 DB를 사용해줘.
   현재 메일과 초안은 프로젝트에 저장하지 말고,
   제목과 본문, 확인이 필요한 정보, 참조한 과거 메일을 채팅에서 보여줘.
   ```

새 메일에 답장할 때는 해당 메일과 작성할 내용을 세션에서 전달합니다. 과거 발신 메일을 추가했다면 먼저 색인을 다시 요청합니다. 같은 파일은 중복 저장하지 않습니다.

### 내부 실행 명령

Codex는 위 요청에 따라 다음과 같은 명령을 실행합니다. 직접 터미널에 입력할 필요는 없습니다.

```sh
# 로그인 상태 확인. 로그인이 필요하면 codex login을 실행합니다.
codex login status

# 폴더의 .eml을 재귀적으로 읽습니다. 수신 메일과 이미 저장한 파일은 건너뜁니다.
./target/release/mimicmail --user me@example.com ingest ./history

# 기본 주소와 별칭을 같은 사용자로 저장합니다.
./target/release/mimicmail --user me@example.com ingest ./history --alias me@work.example

# 수신 메일의 전체 본문(인용 대화 포함)과 작성 요청을 사실의 출처로 사용합니다.
./target/release/mimicmail --user me@example.com draft /path/to/current.eml \
  --to manager@example.com \
  --request '검토 의견에 감사하고 수정본을 2026년 11월 13일까지 전달하겠다고 답장' \
  --role 팀장 --relationship superior
```

GUI에서 복사한 프롬프트는 이 프로젝트 폴더에서 사용합니다. `owner`를 `--user`, `recipient`를 `--to`에 넣어 아래 `context` 명령으로 조회합니다. 기본 DB는 `data/mimicmail.sqlite3`이며 프롬프트에 별도 `DB`가 있으면 `--db`로 지정합니다. 서버 실행 여부와 관계없이 동작하며, DB를 읽기 전용으로 열고 AI 호출 없이 JSON을 반환합니다. 조회 결과의 `selection_instructions`와 `instructions`를 따라 필요한 항목만 추가로 조회하고 초안을 작성합니다. 메일 목적이 정해졌다면 `--purpose request` 등으로 검색 기준을 보완할 수 있습니다.

이 프로젝트에서는 어떤 상황에서도 `Needs input`이나 `request_user_input`, `request_user_input_async` 등 사용자 입력 요청 도구를 사용하지 않습니다. 추가 질문이나 답변 대기 없이 요청과 조회한 자료로 결과를 완성합니다. 확인되지 않은 사실은 만들지 않으며, 없어도 되는 내용은 생략하고 꼭 필요한 누락 정보만 `[확인 필요: 항목]`으로 표시합니다.

```sh
./target/release/mimicmail --user OWNER context --to RECIPIENT

# 후보 목록에서 필요한 식별자만 골라 조회합니다. 각 옵션은 반복할 수 있습니다.
./target/release/mimicmail --user OWNER context --to RECIPIENT \
  --history-key 'sent:선택한메시지키' --style-id '선택한fingerprint'
```

세션에서 원본 메일 바이트를 전달할 때는 파일 경로 대신 `draft -`를 사용하고 표준 입력에 `.eml` 데이터를 전달합니다. 출력 JSON을 Codex가 읽어 채팅에 보여주면 됩니다. 파일로 저장하는 단계는 없습니다.

`--db`(기본 `data/mimicmail.sqlite3`), `--user`, `--backend`, `--model`은 하위 명령 앞에 지정합니다. `--user`는 `ingest`, `draft`, `context`에서 필수이며 `gui`에서는 필요하지 않습니다. `--role`과 `--relationship`은 선택 사항이며, 확인된 정보를 지정하면 자동 분류보다 우선합니다. 별칭으로 색인한 메일도 검색하려면 색인 시 사용한 기본 `--user` 주소를 유지합니다.

Codex 모델은 `--model` 또는 `CODEX_MODEL`로 지정할 수 있으며, 생략하면 Codex CLI의 기본 설정을 사용합니다. 앱 채팅에서 고른 모델이 CLI에 자동 적용되는 것은 아닙니다. 분류는 메일의 외부 수신자마다 한 번, 초안 작성은 분류와 생성에 각각 한 번씩, 참조 후보가 있으면 필요한 항목 선택에 한 번 더 Codex를 실행하므로 처음에는 소량의 메일로 시작하면 결과를 확인하기 쉽습니다.

`draft`는 제목 `subject`, 본문 `body`, 확인할 정보 `missing_facts`, 분류 결과 `classification`, 참조 메일 `style_sources`를 JSON으로 출력합니다. 초안 생성까지 수행하며 이메일 발송 기능은 없습니다.

관계 값: `superior`(상사), `peer`(동료), `subordinate`(부하), `client`(고객), `vendor`(공급자), `academic_advisor`(지도교수), `student`(지도학생), `personal`(개인), `external`(외부 관계자), `unknown`(미상).

### OpenAI API로 실행하는 경우

기존 API 실행 경로도 유지합니다. 이 경우에만 API 키와 Responses API의 Structured Outputs를 지원하는 모델 ID가 필요합니다.

```sh
export OPENAI_API_KEY='YOUR_API_KEY'
export OPENAI_MODEL='YOUR_MODEL_ID'
./target/release/mimicmail --backend openai --user me@example.com ingest ./history
```

## 처리 흐름

1. **추출** — MIME·문자 인코딩·주소를 해석하고, 텍스트 본문을 우선 선택합니다. HTML은 텍스트로 변환합니다. 전체 대화와 직접 작성한 본문을 별도 필드로 유지합니다. 첨부 파일의 내용은 읽지 않습니다.
2. **분류·저장** — `From`이 기본 주소 또는 별칭과 일치하는 메일만 색인합니다. 수신자별로 직책·관계·목적을 분류합니다. 직책·관계의 근거가 원문에 없으면 미상으로 저장합니다. 목적은 `request`, `reply`, `report`, `schedule`, `thanks`, `apology`, `follow_up`, `other` 중 하나입니다. SQLite에 목적·수신자·직책·관계 인덱스를 둡니다.
3. **참조 선택** — 기본 주소로 자료 범위를 제한합니다. 기존 인물은 해당 인물의 이력을, 새 인물은 같은 라벨 전체의 발신 이력을 문체 후보로 제시합니다. 후보 목록을 보고 필요한 본문만 선택하며 다른 라벨이나 단지 목적·관계가 같은 사람으로 범위를 넓히지 않습니다. 동일 인물의 과거 사실은 요청이 이전 대화에 의존할 때만 별도로 선택합니다. `draft --limit N`은 선택할 문체 예시의 최대 수(기본 5)를 정하며 전체 후보 수는 제한하지 않습니다. 여러 수신자에게 보낸 동일 메일은 중복 참조하지 않습니다.
4. **생성** — 현재 대화와 작성 요청은 `current_facts`, 선택한 동일 인물의 이전 사실은 `current_facts.previous_conversation`, 선택한 발신 문체는 `style_references`로 구분해 전달합니다. 선택하지 않은 과거 본문과 후보 목록은 생성 입력에 포함하지 않습니다. GUI에서 복사한 프롬프트도 이 README의 `context` 조회 절차를 따릅니다. 과거 메일의 사실을 새 초안에 옮기지 않도록 지시합니다. 참고할 메일이 없으면 정중하고 간결한 기본 문체를 사용합니다. 필요한 사실이 누락되면 확인 표시를 넣도록 지시합니다.

## 구현 범위와 한계

- 일반적인 영문·한글 답장/전달 구분선, `>` 인용문, HTML `blockquote`, Gmail/Yahoo 인용 영역, Outlook 답장 구분을 제거합니다. 비표준 인용 형식, 구분 없는 복사·붙여넣기, 하단 답장은 완벽하게 판별하지 못합니다. 인용 구분선 뒤의 본문은 보수적으로 제외하므로 일부 사용자 문장이 누락될 수 있습니다.
- 메일의 `From` 헤더를 기준으로 소유자를 판단합니다. 인증이나 발신 진위 검증을 대신하지 않으며, 사용자가 내보낸 메일 보관함을 입력으로 가정합니다.
- 직책·관계 근거의 원문 존재 여부를 검사하지만, 그 근거가 대상 수신자에 관한 것인지의 의미 판단과 최종 사실 준수는 LLM에 의존합니다. 확인된 직책·관계는 옵션으로 지정할 수 있습니다.
- 검색은 분류 값의 정확한 일치를 사용합니다. 벡터 DB나 임베딩, 의미적 유사도 검색은 도입하지 않습니다. 중복 판정은 파일 바이트의 SHA-256 기준이므로 다른 형식으로 다시 내보낸 같은 메일은 별개 자료가 될 수 있습니다.
- 과거 본문은 로컬 SQLite에 저장됩니다. 분류할 메일의 텍스트와 생성에 필요한 현재 대화·검색된 발신 본문은 선택한 Codex 또는 OpenAI API 엔진에 전달됩니다. 로컬 모델로 처리하는 기능은 아닙니다. Codex에는 표준 입력으로 데이터를 전달하며 임시 결과 파일은 처리 후 삭제합니다. Codex 실행에는 `--ephemeral`, OpenAI API에는 `store: false`를 지정하지만, 이것이 제공자의 모든 데이터 보존을 없앤다는 의미는 아닙니다.
- 자동 테스트는 실제 모델 호출 없이 데이터 흐름을 검증합니다. 문체 재현도와 사실 혼입 여부는 실제 자료로 별도 평가해야 합니다.

Codex 연결은 공식 [비대화형 실행 문서](https://learn.chatgpt.com/docs/non-interactive-mode)의 `codex exec --output-schema`를 사용합니다. API 형식은 [Structured Outputs 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)를 따릅니다.

## 상시 실행과 리소스 관리

- HTTP 서버는 단일 비동기 이벤트 루프에서 요청을 기다립니다. 자동 조회나 주기적인 메일 스캔은 수행하지 않습니다.
- 동시 HTTP 연결은 최대 16개, DB 작업은 최대 2개입니다. DB 작업 슬롯이 차면 최대 500ms 동안 기다린 뒤 503을 반환합니다. 대기는 최대 연결 수 안에서만 발생합니다.
- HTTP 헤더는 5초, 연결 전체는 30초로 제한합니다. SQLite 잠금 대기는 2초이며, 요청의 SQL 실행과 조회용 본문 처리에는 10초 제한을 적용합니다. 연결이 끊기면 SQLite 진행 콜백과 Rust 처리 루프에 취소를 전달합니다.
- JSON 변경 요청은 1,000,000바이트, 가져오는 메일과 표준 입력은 64 MiB, 모델 응답은 4 MiB까지 처리합니다. 초과 입력은 오류로 알립니다.
- DB 연결·문장·요청 데이터는 작업 완료 시 해제합니다. 스키마 초기화는 서버 시작 시 한 번 수행하며 메일 본문을 전역 캐시에 계속 쌓지 않습니다.
- 목록 요약과 병합된 대화는 SQLite의 `browse_*` 조회용 테이블에 저장합니다. 최초 조회 시 만들고, 메일·편집·라벨·삭제·상대 답장이 바뀌면 관련 대화만 갱신합니다. 다른 CLI나 프로세스의 변경도 트리거로 감지하며, 변경 없는 조회는 DB를 쓰지 않습니다. 캐시의 형식 버전이 바뀌면 원본에서 재구성합니다.
- 브라우저는 최근 메시지 50개와 필요한 메타데이터만 받고 **이전 메시지 / 다음 메시지**로 이동합니다. 이전 페이지의 데이터와 DOM은 교체하며, 전체 검색 건수·이전/다음 검색 이동은 페이지 밖의 결과에도 적용됩니다. 인용 중복 제거는 페이지를 나누기 전에 수행합니다. 원문·편집 자료는 편집기를 열 때 조회합니다. 검색·대화 전환 시 이전 조회를 취소하며, 편집기를 닫으면 보관하던 원문을 해제합니다.
- Codex 호출은 180초, API 호출은 120초로 제한합니다. Codex 표준 출력·오류를 메모리에 누적하지 않으며, 제한 시간에는 자식 프로세스 그룹을 종료하고 임시 파일을 정리합니다.
- 기존 SQLite 스키마, 편집본, 수정 버전과 논리 삭제 키를 유지합니다. Rust 이관을 위해 기존 메일을 다시 색인할 필요가 없습니다.

이 제한은 동시 작업과 입력 크기를 제어합니다. 전체 메모리에 고정된 상한을 보장하지는 않습니다. 조회용 인덱스를 처음 만들거나 무효화된 대화를 재구성할 때는 해당 대화의 전체 본문을 처리하므로 메일 수와 본문 크기에 따라 작업 메모리가 달라집니다. 반복 조회의 CPU 사용과 화면 메모리를 줄이는 대신 DB 파일 크기와 최초 인덱스 작성 비용이 늘어납니다. 작성 요청은 기존처럼 열린 페이지 메모리에만 유지하며 자동으로 삭제하지 않습니다.

### 리소스 비교 재현

최적화 전후의 release 실행 파일을 각각 준비한 뒤 macOS에서 실행합니다. Python 표준 라이브러리만 사용하며, 실제 DB는 읽기 전용으로 복사하고 모든 부하 요청은 임시 복사본과 합성 DB에 보냅니다. 실행 중인 서버나 원본 메일 DB를 변경하지 않습니다.

```sh
python3 scripts/benchmark_resources.py \
  --before /path/to/before/mimicmail \
  --after target/release/mimicmail \
  --db data/mimicmail.sqlite3 \
  --output /tmp/mimicmail-resources.json
```

목록·검색·대화의 첫 요청과 반복 20회 응답 시간, 요청당 서버 CPU 시간, macOS physical footprint·최대 footprint, DB 크기, 30초 유휴 사용량과 취소된 검색의 CPU 시간을 기록합니다. 긴 대화는 기존 전체 응답과 새 화면의 첫 50개 응답을 비교합니다. 브라우저 메모리는 별도로 측정하며 이 스크립트의 서버 메모리에 포함하지 않습니다.

## GitHub에 올리기 전 확인

소스 코드, 테스트, 실행 파일, 패키지 설정과 문서를 Git으로 관리합니다. 로컬 메일 자료인 `data/`, `history/`, 메일 원본(`*.eml`, `*.mbox`), SQLite 파일, 환경설정 파일(`.env`, `.env.*`), 가상환경과 빌드 결과는 `.gitignore`로 제외합니다. API 키는 환경변수로 설정하고 소스나 문서에 기록하지 않습니다.

아래 명령으로 추가 대상과 제외된 파일을 확인할 수 있습니다. 파일을 스테이징하거나 커밋하지 않습니다.

```sh
git status --short --untracked-files=all
git status --short --ignored
```

새로 내려받은 프로젝트에서는 위의 Rust 빌드 과정을 진행합니다. `data/`는 실행 시 자동 생성되며, `history/`를 사용하려면 직접 만들거나 기존 메일 보관 폴더를 지정합니다.
